# Carbon Data Layer

This directory is the normalized carbon-footprint data layer for the new
product-footprint feature.

Raw source material stays outside this directory in:

- `totalCarbonfootprintcalculation/`

This normalized layer is intended to be stable and machine-readable:

- `products/`
  Product-specific JSON profiles with identity, defaults, life-cycle inputs,
  provenance, and data-quality status.
- `factors/`
  Curated factor tables used by the deterministic calculator.
- `mappings/`
  Manual mapping files that connect canonical categories in our system to
  source-specific workbook rows or flow names.
- `extracted/`
  Readable text extracts and source summaries generated from raw PDFs and
  workbooks.
- `build_manifest.json`
  A machine-readable build summary showing what was extracted, skipped, or
  still blocked.

Status conventions:

- `grounded`
  Directly extracted from a source file with no model-driven guessing.
- `estimated`
  A temporary working assumption derived from a nearby product or source.
- `pending_official_extraction`
  The field exists in the schema but still needs official source extraction.
- `needs_manual_curation`
  The source exists but the correct row/flow/category mapping is not ready yet.

Current scope after Steps 1 and 2:

- A normalized starter product profile for `Lexmark MX431adn`.
- A grounded electricity factor table from the CoM workbook generated by the
  builder script.
- Placeholder factor tables for raw materials, transport, and end-of-life.
- A manual mapping template for later EF workbook curation.
- Extracted text files for readable PDFs.
- A build manifest and source-extract index.

Build command:

- `python3 scripts/build_carbon_assets.py`

Deterministic calculator:

- `backend/services/carbon_calculation_service.py`
- The calculator returns stage-by-stage traces, recyclability metrics, and
  explicit missing-input diagnostics.
- If all requested stages are computable, it returns a complete total.
- If inputs or factors are missing, it returns a partial result instead of
  fabricating a full carbon-footprint number.
- The current scenario override interface accepts both the normalized field
  names and the Step 3 implementation aliases such as `mode_key`,
  `factor_value_kg_co2e_per_kg`, `factor_value_kg_co2e_per_ton_km`,
  `electricity_country_code`, `electricity_year`, `recyclability_pct`, and
  nested end-of-life `route_factors`.

Typed API schemas:

- `backend/api/carbon_models.py`
- Provides typed request models for carbon-calculation payloads and typed
  response models for calculator outputs.
- Includes conversion helpers between the API schema layer and the
  deterministic calculation service.

Solve integration:

- `backend/services/carbon_query_service.py`
- Carbon and recyclability questions can now be routed through the existing
  `/solve` endpoint.
- The solve integration currently supports `Lexmark MX431adn`.
- Answers are built from deterministic calculation outputs plus synthetic
  context passages, with deterministic fallback wording when no LLM backend is
  available.

Debug endpoint:

- `backend/api/carbon.py`
- `GET /carbon/products` lists supported normalized product ids.
- `POST /carbon/calculate` returns structured calculator output directly,
  using the typed carbon request/response schemas.
- The endpoint supports both partial official-data inspection and full
  override-based debugging runs.

Ontology sidecar:

- `backend/ontologies/carbon_ontology.ttl`
- `backend/services/carbon_ontology_service.py`
- The ontology sidecar represents products, scenarios, stages, activities,
  factors, results, units, statuses, and source provenance as RDF.
- `POST /carbon/calculate` can optionally return ontology validation metadata
  and a Turtle serialization for debugging and research traceability when
  `include_ontology_sidecar` and `include_ontology_turtle` are enabled.
- The ontology validates structure and provenance coverage; it does not replace
  the deterministic arithmetic engine.

Generated answer assets:

- `backend/services/carbon_answer_assets_service.py`
- `scripts/build_carbon_answer_assets.py`
- `backend/data/carbon/corpus/carbon_docs.jsonl`
- `backend/data/carbon/corpus/carbon_docs_manifest.json`
- The answer-asset builder materializes reusable context passages for:
  - carbon overview
  - total footprint
  - raw materials
  - transportation
  - use phase
  - end of life
  - recyclability
  - missing inputs
- Build command:
  - `python3 scripts/build_carbon_answer_assets.py`
- The generated corpus keeps raw-material and transportation passages separate,
  so the system can answer stage-specific questions instead of only total
  carbon-footprint queries.
- The `/solve` carbon path reuses the same shared answer-asset generator at
  runtime, keeping generated corpus rows and live carbon answers aligned.

Tests:

- `tests/test_carbon_service.py`
- `tests/test_carbon_solve.py`
- `tests/carbon/test.jsonl`
- Recommended command:
  - `.venv/bin/python -m unittest tests.test_carbon_service tests.test_carbon_solve -v`
- The solve-route tests use a lightweight FastAPI app plus import stubs for
  non-carbon solve dependencies so the carbon interception path can be tested
  without requiring optional router packages such as `pandas`.

Estimate fallback and provenance disclosure:

- `backend/data/carbon/products/lexmark_mx431adn.json`
- `backend/services/carbon_calculation_service.py`
- `backend/services/carbon_query_service.py`
- The Lexmark profile now contains:
  - `observed_facts`
  - `estimation_profile`
- The calculator now distinguishes:
  - `exact`
  - `hybrid_estimate`
  - `scenario_override`
  - `partial`
- Calculation outputs now include:
  - `quality_status`
  - `estimated_fields`
  - `provenance`
  - `uncertainty_pct`
  - `uncertainty_kg_co2e`
  - `uncertainty_range_kg_co2e`
- `/solve` now follows an exact-first policy:
  - try official normalized data first
  - if that is incomplete, fall back to the explicit estimate profile
  - if the user asks for `exact only`, `official only`, or `no estimate`, keep
    the result partial instead of silently estimating
- User-facing answers should now say when a total is an estimate, show the
  approximate uncertainty, and name the main estimated inputs and sources.

Important notes:

- The raw `Lexmark MX431adn.pdf` could not be text-extracted yet because it is
  encrypted. Quantitative product inputs therefore remain explicit placeholders
  until later extraction work.
- The EF workbook is too broad to query directly at runtime. It needs curated
  mappings first.
- The generated answer corpus currently reflects the real repo state honestly:
  because official MX431adn product inputs remain incomplete, the current
  answer assets are partial and include explicit missing-input diagnostics.
